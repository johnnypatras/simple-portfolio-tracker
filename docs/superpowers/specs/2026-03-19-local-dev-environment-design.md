# Local Dev Environment Separation

**Date**: 2026-03-19
**Status**: Design approved, pending implementation
**Goal**: Isolate local development from production database so `npm run dev` can never accidentally modify production data.

## Problem

`.env.local` currently points to the production Supabase instance (`jaxjhmkehoyrkcxpbzay.supabase.co`). Every `npm run dev` session, every server action tested locally, every transfer/edit/delete hits real data. Migrations applied via MCP go directly to production. A bug in local dev code can corrupt production data.

## Solution Overview

```
Production DB ──(pg_dump)──→ Local DB              # npm run dev (auto) / npm run sync (manual)
Local DB ──(migrations)────→ Production DB          # npm run db:push-schema (CI or manual)
Local DB ──(full dump)─────→ Production DB          # npm run db:push-data (rare, guarded)
```

Local dev always uses local Supabase Docker. Production is only touched by CI pipeline or explicit push commands.

## Section 1: Environment File Reorganization

### File Layout

| File | Purpose | Loaded by Next.js? | Git |
|------|---------|---------------------|-----|
| `.env.local` | Local Supabase keys (auto-generated by sync) | Yes | Ignored |
| `.env.remote` | Production credentials (sync/push scripts only) | No — not in Next.js loading chain | Ignored |
| `.env.remote.example` | Template for `.env.remote` | No | Committed |
| `.env.example` | General onboarding template (existing) | No | Committed |
| `.env.sentry-build-plugin` | Sentry auth token for source map uploads (existing, unchanged) | No | Ignored |

### Why `.env.remote` and not `.env.production.local`

Next.js auto-loads `.env.production.local` when `NODE_ENV=production` (e.g., during `npm run build`). Using `.env.remote` — a name outside Next.js conventions — guarantees Next.js never touches production credentials regardless of build mode.

### `.env.remote` contents

```bash
# Production Supabase — used ONLY by sync/push scripts, never by Next.js
# IMPORTANT: Use session pooler (port 5432), NOT transaction pooler (port 6543).
# Get from: Supabase Dashboard → Connect → Session Pooler
# pg_dump requires a session-level connection (COPY protocol, etc.)
# Values with special characters ($, spaces, !) MUST be single-quoted.
REMOTE_DATABASE_URL='postgresql://postgres.[ref]:[password]@aws-0-[region].pooler.supabase.com:5432/postgres'
REMOTE_SUPABASE_URL=https://jaxjhmkehoyrkcxpbzay.supabase.co
REMOTE_SUPABASE_SERVICE_ROLE_KEY=sb_secret_...
COINGECKO_API_KEY=CG-...
SENTRY_DSN=https://...
```

The `REMOTE_` prefix makes it explicit: these are production values, read only by scripts.

### Auto-generated `.env.local`

Written by the sync script from `supabase status --output json`:

```bash
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
NEXT_PUBLIC_SUPABASE_ANON_KEY=<from supabase status>
SUPABASE_SERVICE_ROLE_KEY=<from supabase status>
COINGECKO_API_KEY=<copied from .env.remote>
NEXT_PUBLIC_SENTRY_DSN=<copied from .env.remote>
SENTRY_DSN=<copied from .env.remote>
```

Safety guarantee: even if the sync script is bypassed, `.env.local` points to localhost.

### Runtime safety guard (defense in depth)

In `src/lib/supabase/server.ts` (or a shared init module), add a runtime check:

```typescript
if (process.env.NODE_ENV === 'development') {
  const url = process.env.NEXT_PUBLIC_SUPABASE_URL;
  if (url) {
    try {
      const h = new URL(url).hostname;
      if (h.endsWith('.supabase.co') || h === 'supabase.co') {
        throw new Error('SAFETY: Development server is pointing to production Supabase. ' +
          'Run `npm run sync` to regenerate .env.local with local credentials.');
      }
    } catch (e) { if (e instanceof Error && e.message.startsWith('SAFETY:')) throw e; }
  }
}
```

This protects against `.env.local` being accidentally overwritten with production credentials — regardless of whether `npm run dev` or `npm run dev:skip-sync` is used.

### `.gitignore` updates

Replace the existing env section (lines 35-36 and line 73) with:

```
# env files
.env*
!.env.example
!.env.remote.example
backups/
```

Note: the separate `.env.sentry-build-plugin` line is removed because `.env*` already covers it.

## Section 2: Sync Mechanism (Production → Local)

### Script: `scripts/sync-db.sh`

**Flow:**

1. **Verify Docker** — exit with message if Docker daemon not running.
2. **Verify local Supabase** — if not running, start it (`supabase start`).
3. **Read `.env.remote`** — exit with setup instructions if missing.
4. **pg_dump DATA from production** — data only (`--data-only`) for `public` schema tables.
   - Dumps all 18 app tables (crypto_assets, stock_positions, cash_accounts, activity_log, etc.)
   - Format: custom (`-Fc`) for efficient restore
5. **pg_dump auth DATA** — data only from specific auth tables:
   - `auth.users`, `auth.identities`, `auth.mfa_factors`, `auth.mfa_challenges`
   - NOT the full auth schema (GoTrue manages its own schema DDL and migrations)
6. **Truncate local `public` tables** — clear existing data while preserving schema (managed by migration files).
7. **Truncate local auth data tables** — clear `auth.users`, `auth.identities`, `auth.mfa_factors`, `auth.mfa_challenges`.
8. **pg_restore data** into local Docker Postgres (port 54322).
   - Flags: `--data-only --no-owner --disable-triggers` (restore data without DDL conflicts)
9. **Apply pending local migrations** — if any migration files in `supabase/migrations/` haven't been applied locally yet, run `supabase migration up`.
10. **Write `.env.local`** — read local keys from `supabase status --output json`, copy non-Supabase vars from `.env.remote`.
11. **Print summary** — "Synced N tables, M auth users from production."

**Why data-only, not schema+data?** Schema is managed by migration files (single source of truth). GoTrue manages the `auth` schema DDL internally. Restoring full schema from production would conflict with both. Data-only sync avoids GoTrue version mismatches and migration history idempotency issues.

### What's synced vs excluded

| Schema | Synced? | Reason |
|--------|---------|--------|
| `public` (data only) | Yes | All 18 app tables — data only, schema comes from migration files |
| `auth` (data only) | Yes | `auth.users`, `auth.identities`, `auth.mfa_factors`, `auth.mfa_challenges` — data only, GoTrue manages schema DDL |
| `auth` (schema) | No | GoTrue manages its own schema and internal migrations — overwriting would cause version conflicts |
| `supabase_migrations` | No | Local migration history is managed by `supabase db reset` / `supabase migration up` from migration files |
| `storage` | No | Supabase Storage internals — not used by this app |
| `realtime` | No | Supabase Realtime internals — local service manages its own state |
| `supabase_functions` | No | Edge Function metadata — local has its own function serving |

### Auth handling

- Bcrypt password hashes are portable — same email/password works locally
- Local Supabase has a different JWT signing secret — you must log in fresh (no session sharing)
- MFA enrollments are synced for future-proofing (not currently used)
- Email confirmation timestamps are preserved — no re-verification needed locally

### Error handling

| Failure | Behavior |
|---------|----------|
| Docker not running | "Docker is not running. Start Docker Desktop and retry." Exit 1. |
| `.env.remote` missing | "Missing .env.remote. Copy .env.remote.example and fill in production credentials." Exit 1. |
| Production DB unreachable | "Cannot connect to production database. Check network and .env.remote." Exit 1. |
| pg_dump/restore fails | Print PG error. Exit 1. Dev server does NOT start. |
| Local Supabase not running | Auto-start via `supabase start`. |

Key principle: if sync fails, `npm run dev` does NOT proceed. You never develop against stale/broken data unknowingly.

### npm scripts

```json
{
  "dev": "bash scripts/sync-db.sh && next dev --turbopack",
  "dev:skip-sync": "echo '⚠ Skipping sync — using existing local data.' && next dev --turbopack",
  "dev:edge": "supabase functions serve daily-snapshot --env-file .env.local",
  "sync": "bash scripts/sync-db.sh",
  "db:push-schema": "bash scripts/push-schema.sh",
  "db:push-data": "bash scripts/push-data.sh",
  "db:restore-backup": "bash scripts/push-data.sh --restore"
}
```

| Command | Purpose |
|---------|---------|
| `npm run dev` | Sync production → local, then start dev server (default, safe) |
| `npm run dev:skip-sync` | Skip sync, fast restart mid-session. Prints warning: "Skipping sync — using existing local data." |
| `npm run dev:edge` | Serve Edge Functions locally for testing |
| `npm run sync` | Standalone sync anytime (e.g., after recording a trade in production) |

### `supabase db reset` vs `npm run sync`

| Command | What it does | Data after |
|---------|-------------|------------|
| `npm run sync` | Copies production DATA into existing local schema | Full production data |
| `supabase db reset` | Drops everything, replays all migration files from scratch | Correct schema, empty tables |

These serve different purposes:
- **`npm run sync`** — for daily development (get fresh data on existing schema)
- **`supabase db reset`** — for migration development (verify migrations replay cleanly from scratch)

After `supabase db reset`, the next `npm run dev` re-syncs production data.

Note: `npm run sync` requires the local schema to match production. If production has migrations not yet in your local files (e.g., you haven't `git pull`ed), the data restore may fail due to schema mismatches. Always `git pull` before syncing.

## Section 3: Push-to-Production Commands

### `npm run db:push-schema` — Routine, moderate risk

**Script:** `scripts/push-schema.sh`

**Flow:**

1. Read `REMOTE_DATABASE_URL` from `.env.remote`.
2. Dry-run: `supabase db push --db-url $REMOTE_DATABASE_URL --dry-run` — shows which migrations would be applied.
3. Prompt: "Apply N migration(s) to PRODUCTION? [y/N]" (default No).
4. Apply: `supabase db push --db-url $REMOTE_DATABASE_URL`.
5. Print: "Applied migrations 007, 008 to production."

**Safeguards:** dry-run preview, interactive confirmation, schema-only (no data changes).

### `npm run db:push-data` — Rare, high risk

**Script:** `scripts/push-data.sh`

**Flow:**

1. Read `REMOTE_DATABASE_URL` from `.env.remote`.
2. Print WARNING banner about destructive overwrite.
3. Require `--confirm` flag (exits without it).
4. Back up production: `pg_dump production → backups/pre-push-YYYY-MM-DD-HHMMSS.dump` (custom format, compressed).
5. Prompt: type exact phrase `OVERWRITE PRODUCTION` to proceed.
6. `pg_dump` local → `pg_restore` to production.
7. Print: "Production overwritten. Backup at backups/pre-push-..."

**Safeguards:** `--confirm` flag, auto-backup, exact phrase confirmation, `backups/` gitignored.

**Auth data warning:** This command overwrites production auth data (users, passwords, MFA enrollments) with local copies. If you created test users locally or changed passwords, those changes will overwrite production. Use `db:push-schema` (migrations only) unless you explicitly need a full data overwrite.

### `npm run db:restore-backup` — Emergency rollback

Takes backup file path as argument. Safeguards: warning banner, auto-backup of current production state, type exact phrase `OVERWRITE PRODUCTION`. Note: `--confirm` flag is not required for restore (the backup file argument itself is an intentional action, and the type-phrase gate is sufficient).

### Command summary

| Command | Risk | Confirmation | Frequency |
|---------|------|-------------|-----------|
| `npm run sync` | None (read-only) | None | Every dev session |
| `npm run db:push-schema` | Moderate | Dry-run + y/N | Per feature with migrations |
| `npm run db:push-data` | High | `--confirm` + type phrase + auto-backup | Almost never |
| `npm run db:restore-backup` | High | Type phrase + auto-backup | Emergency only |

## Section 4: CI/CD Pipeline

### Current state (risky)

- GitHub Actions (`test.yml`): tests only
- Vercel: auto-deploys on push to main (independent of tests)
- Edge Function deploy (`deploy-edge-function.yml`): separate workflow
- Race condition: code deploys before migration applies, or vice versa

### New state (safe)

Single unified pipeline. Vercel auto-deploy disabled.

```
PR to main:
  └── test job: lint → build → unit → component → supabase start → integration → stop
        ↓ (passes)
  └── preview job: vercel deploy (preview URL for PR)

Push to main:
  └── test job (same as above)
        ↓ (passes)
  └── deploy job:
        ├── supabase db push --linked (if migrations changed; uses SUPABASE_ACCESS_TOKEN + PROJECT_REF)
        ├── vercel deploy --prod (uses VERCEL_TOKEN + ORG_ID + PROJECT_ID)
        └── supabase functions deploy (if functions changed)
```

### CI vs local push commands

| Context | Migration command | Auth mechanism |
|---------|------------------|----------------|
| **CI (deploy job)** | `supabase db push --linked` | `SUPABASE_ACCESS_TOKEN` + `SUPABASE_PROJECT_REF` GitHub secrets |
| **Local manual** | `supabase db push --db-url $REMOTE_DATABASE_URL` | Session pooler connection string from `.env.remote` |

These are two invocation modes of the same `supabase db push` command. CI uses `--linked` (token-based, non-interactive). Local uses `--db-url` (connection string, interactive with dry-run preview).

### Preview deployments

Preview deployments for PRs use Vercel's configured environment variables (production Supabase). This is acceptable because previews are read-mostly and the solo developer controls all PRs. Supabase branching (preview databases per PR) can be added later if needed.

### Fail-fast semantics

| Scenario | Tests | Migration | Deploy | Result |
|----------|-------|-----------|--------|--------|
| Tests fail | FAIL | Skipped | Skipped | Nothing changes |
| Tests pass, migration fails | PASS | FAIL | Skipped | Nothing deploys |
| Tests pass, migration succeeds | PASS | PASS | Runs | Full deployment |
| Tests pass, no pending migrations | PASS | Skip (no-op) | Runs | Code deployed |

### Workflow consolidation

| Current | New |
|---------|-----|
| `test.yml` | `ci.yml` (unified) |
| `deploy-edge-function.yml` | Absorbed into `ci.yml` deploy job |
| `claude.yml` | Unchanged |
| `claude-code-review.yml` | Unchanged |

### Concurrency control

```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
  # PRs: cancel previous runs on same branch (fast feedback)
  # Main: queue sequentially per-ref (never cancel running deploys)
```

### Required GitHub secrets

| Secret | Status |
|--------|--------|
| `SUPABASE_ACCESS_TOKEN` | Exists |
| `SUPABASE_PROJECT_REF` | Exists |
| `SENTRY_AUTH_TOKEN` | Exists |
| `VERCEL_TOKEN` | **New** — from vercel.com/account/tokens |
| `VERCEL_ORG_ID` | **New** — from `.vercel/project.json` after `vercel link` |
| `VERCEL_PROJECT_ID` | **New** — from `.vercel/project.json` after `vercel link` |

### Backward-compatible migration convention

Since migrations apply before code deploys, there's a brief window where production has new schema + old code. Migrations MUST be backward-compatible:

- Add columns as nullable or with defaults (old code ignores them)
- Never rename/drop columns in the same PR that removes their usage
- Two-step breaking changes: deploy code that handles both → migrate → deploy cleanup

## Section 5: One-Time Migration

### Prerequisites

- Docker Desktop running
- Local Supabase running (`supabase start`)
- Production database connection string from Supabase Dashboard → Connect → Session Pooler (port 5432, NOT transaction pooler on 6543)

### Steps

1. **Move credentials**: `mv .env.local .env.remote`, add `REMOTE_DATABASE_URL`.
2. **Create `.env.remote.example`**: committed template.
3. **Create scripts**: `scripts/sync-db.sh`, `scripts/push-schema.sh`, `scripts/push-data.sh`.
4. **Update `package.json`**: add `dev`, `dev:skip-sync`, `dev:edge`, `sync`, `db:push-schema`, `db:push-data`, `db:restore-backup` scripts.
5. **Run first sync**: `npm run sync` — generates `.env.local` with local keys, populates local DB.
6. **Verify**: `npm run dev` → open browser → log in → confirm all data present.
7. **Update `.gitignore`**: add `!.env.remote.example`, `backups/`.
8. **Set up Vercel CLI**: `vercel link`, note org/project IDs, add GitHub secrets.
9. **Disable Vercel auto-deploy**: Vercel Dashboard → Settings → Git.
10. **Replace CI workflows**: `test.yml` + `deploy-edge-function.yml` → `ci.yml`.
11. **Verify CI**: push test branch, confirm tests + preview URL. Merge, confirm deploy pipeline.

### Rollback

| Problem | Fix |
|---------|-----|
| Local dev broken | Copy `.env.remote` back to `.env.local` |
| CI deploy not working | Re-enable Vercel auto-deploy in dashboard |
| Sync script buggy | `npm run dev:skip-sync` while debugging |
| CI migration breaks production | Revert migration via Supabase Dashboard SQL editor, or `npm run db:restore-backup` if a backup exists. Consider adding a pre-migration backup step in CI for critical migrations. |

Zero production downtime risk. All changes are local or CI configuration.

## Known Behaviors (Not Issues)

| Behavior | Why it's fine |
|----------|--------------|
| Must log in fresh locally (no session sharing) | Different JWT secrets; bcrypt passwords are portable |
| pg_cron jobs don't fire locally | Intentional — no automated snapshots against test data. Existing snapshots are synced. |
| Edge Functions need `supabase functions serve` for local testing | Separate from dev server; `npm run dev:edge` provided |
| `pg_stat_statements` may not be available locally | Not used by app code — DBA monitoring only |
| `.env.sentry-build-plugin` unchanged | Build credential (source map uploads), not a runtime credential |

## Post-Migration State

```
Local development:
  .env.local         → 127.0.0.1:54321 (auto-generated, safe)
  .env.remote        → production credentials (scripts only)
  npm run dev        → sync + dev server (always safe)

Production:
  Vercel env vars    → production Supabase (unchanged)
  GitHub secrets     → deploy credentials
  Deploys            → GitHub Actions only (no auto-deploy)

CI Pipeline:
  PR to main         → tests + preview deploy
  Push to main       → tests → migrate → deploy → deploy edge functions
```
